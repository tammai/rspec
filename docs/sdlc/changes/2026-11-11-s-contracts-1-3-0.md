# Copy contracts 1.3.0, and never write an [inferred] criterion at level 1

## Why

**Request (verbatim):** "Merge both, then copy (Recommended)" (to: merge rspec #15 and product-rebuild #6, then copy contracts 1.3.0 into rspec with a guard so an old audit levels file can't put an `[inferred]` criterion at level 1).

Contracts 1.3.0 (product-rebuild f4ac06e) makes `check_lock` reject a criterion tagged `inferred` at level 1. rspec's own audit stopped producing that in 0.12.0, but two older sources can still feed it to `write_lock`: an `audit/levels.json` drawn before 0.12.0, and a lock written before it (its level is carried while the text is unchanged). Without a guard, `check_spec.py` would fail on such a spec instead of lowering the level.

## Decisions

| Decision | Ruled out | Why |
|---|---|---|
| `write_lock` sets an `[inferred]` criterion at level 1 to 0, with a warning to rerun `audit_sample.py --levels` | Letting `check_lock` fail the run | The level is stale, not the spec; a lower level is the honest answer and the run stays usable |
| Copy the 10 files byte-identical (9 changed, 1 new fixture) | Editing the copy | Constitution I |

## Acceptance criteria

- **AC-001** Given a spec, when `check_spec.py` writes the lock, then it records `"contracts": "1.3.0"`, and the vendored folder matches its MANIFEST.
- **AC-002** Given an `[inferred]` criterion that an old `audit/levels.json` (or an old lock) has at level 1, when `check_spec.py` runs, then it exits 0, the lock has it at level 0, and a warning names it and says to rerun `audit_sample.py --levels`.

No review ran: no trigger fired (S, low risk, no public surface). AC-001 and AC-002 red then green; contracts/v1 matches product-rebuild f4ac06e byte for byte.
