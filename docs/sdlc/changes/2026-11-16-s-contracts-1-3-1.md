# check_spec accepts an equiv-trace departure: vendor contracts 1.3.1

## Why

**Request (verbatim):** "go" — re-vendor shared contracts 1.3.1 into rspec, after the same bug was fixed for bug-hunter (tammai/bug-hunter#36) in the canonical contracts (tammai/product-rebuild#11).

**Proof:** `check_spec.py` on a spec whose `departures.yaml` holds `match: [{runner: http, rule: "equiv-trace:invoices-total"}]` (what product-rebuild's `equiv.py accept` writes into a workbench's `docs/departures.yaml`) exits 1 with `ERROR departures.yaml: D-005 match 1: unknown rule equiv-trace:invoices-total (uuid, int, iso8601, same-as:<capture>, regex:<pattern>)`.

**Root cause:** vendored `contracts/v1/contracts.py` 1.3.0 `check_departures` checks match rules against the HTTP replay step vocabulary, which has no `equiv-trace:`.

## Decisions

- Vendor 1.3.1 byte-identical from product-rebuild; no change to `check_spec.py`. Ruled out: filtering the error in `check_spec.py`, which would make rspec's reading of C5 differ from the shared contract.

## Acceptance criteria

- **AC-001** Given a spec whose `departures.yaml` has an accepted `equiv-trace:<name>` entry, when `check_spec.py` runs, then it exits 0.
- **AC-002** Given `contracts/v1/` vendored at 1.3.1, then `vendor-check` passes and the lock records contracts 1.3.1.
